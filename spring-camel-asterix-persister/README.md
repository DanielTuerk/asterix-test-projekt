# spring-camel-asterix-persister

Spring Boot 4.1 + Apache Camel 4.22 (Java 21). Eine Camel-Route liest die Rohbloecke vom
Kafka-Topic, loggt sie als Hexdump und schreibt sie unveraendert nach PostgreSQL.

## Aufbau

| Datei | Zweck |
| --- | --- |
| `AsterixPersisterApplication` | Spring-Boot-Einstiegspunkt (kein Web-Server) |
| `AsterixPersisterRoute` | die Camel-Route: `from(kafka) -> loggen -> Parameter-Map -> to(sql)` |
| `application.yaml` | Topic, Broker, Datenbank und das INSERT-Statement |
| `schema.sql` | legt die Tabelle `asterix_raw` an, falls sie fehlt |

Die Route in Kurzform:

```java
from("{{asterix.source.uri}}")
        .convertBodyTo(byte[].class)
        .process(this::logBody)
        .process(this::toSqlParameters)
        .to("{{asterix.sink.uri}}");
```

Auch hier wird der Datensatz nicht angefasst: in `payload` landen exakt die Bytes vom Topic.
Alles andere (`stored_at`, `kafka_*`) ist Herkunftsinformation, kein Inhalt.

## Die Tabelle

```sql
CREATE TABLE IF NOT EXISTS asterix_raw (
    id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    stored_at       TIMESTAMP WITH TIME ZONE NOT NULL,  -- Zeitpunkt des INSERT
    kafka_timestamp TIMESTAMP WITH TIME ZONE,           -- Zeitstempel des Kafka-Records
    kafka_topic     VARCHAR(255),
    kafka_partition INTEGER,
    kafka_offset    BIGINT,
    payload         BYTEA NOT NULL                      -- der unveraenderte ASTERIX-Block
);
```

`spring.sql.init.mode: always` sorgt dafuer, dass `schema.sql` bei jedem Start laeuft -
dank `IF NOT EXISTS` ist das gefahrlos. Das Statement ist bewusst so geschrieben, dass
PostgreSQL und H2 es gleichermassen verstehen; der Unit-Test braucht darum kein Docker.

## Zwei Camel-Details

**Deserializer.** Camels Kafka-Default ist der `StringDeserializer` und wuerde an rohen
ASTERIX-Bytes scheitern. Darum steht in der Quell-URI
`valueDeserializer=org.apache.kafka.common.serialization.ByteArrayDeserializer`.

**Benannte SQL-Parameter.** camel-sql schreibt sie als `:#name`. Camel ersetzt das `#`
intern durch `?` - in der URI selbst waere ein `?` der Trenner zu den Optionen und wuerde
das Statement zerreissen. Die Werte sucht camel-sql zuerst in einer `Map` im Body, dann in
den Headern; deshalb baut `toSqlParameters` den Body zur Parameter-Map um.

## Starten

Erst die Infrastruktur (Modul `asterix-infra`), dann:

```powershell
.\mvnw.cmd -pl spring-camel-asterix-persister spring-boot:run
```

Erwartete Log-Ausgabe, sobald der Receiver etwas auf das Topic legt:

```
ASTERIX-Block aus Kafka gelesen (topic=asterix-raw, partition=0, offset=17) - 11 Byte
0000  30 00 0B F5 02 0D E0 1A B4 2F 08
```

## Tests

```powershell
.\mvnw.cmd -pl spring-camel-asterix-persister test
```

| Test | Was er prueft | Docker noetig |
| --- | --- | --- |
| `AsterixPersisterRouteTest` | Route gegen `direct:` und H2: Block landet unveraendert in `asterix_raw` | nein |
| `AsterixPersisterEndToEndIntegrationTest` | echter Broker + echtes PostgreSQL aus Containern | ja (sonst schlaegt er fehl) |

## Andere Datenbank

Alles laeuft ueber die normale Spring-DataSource. Fuer eine andere Instanz genuegt:

```powershell
.\mvnw.cmd -pl spring-camel-asterix-persister spring-boot:run `
  "-Dspring-boot.run.arguments=--spring.datasource.url=jdbc:postgresql://host:5432/db"
```
